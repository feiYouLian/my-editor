## 3 P1-1 决策：不拆分独立 capability，判据收敛为纵深防御

计划 S3-2 的原始判据是「破坏性命令归入独立 capability」。收口时未采用该路线，理由与现状：

- Tauri 2 的 capability 按窗口 / 来源授权；本应用只有一个 `main` 窗口，把破坏性命令拆到独立
  capability 再授予同一窗口，与 `default.json` 一揽子授予没有差别——真正的 ACL 隔离要等多窗口
  或嵌入不受信 WebView 的场景才有意义。
- 自定义命令进入 ACL 需要 app-manifest 权限定义；一旦启用，全部 102 个命令都要补权限声明，
  漏一个就是运行时不可用（只有 E2E 能发现），对单窗口收益近似为零。
- 实际采用并已落地的纵深防御：
  - 配置目录写保护：`paths.rs` 的 `protect_dir` / `is_protected`，启动登记配置目录，伪造登记也写不进；
  - 破坏性操作备份：`git_discard` 的 `discard-backup` 快照 + `ensure_writable`；
  - 执行面收敛：终端 shell 白名单且拒绝路径形态（`terminal.rs:121` SUPPORTED_SHELLS / `terminal.rs:134`）；
    运行器 program 准入 + 参数拒绝清单（P0-1，§2）；
  - 护栏：IPC 契约 / panic 点 / DOM 注入面三道静态门禁 + E2E 拒绝用例。
- 后续若引入多窗口或不受信内容 WebView，再按计划原判据拆分 capability；届时以本节为变更入口。
- 计划文档（仓库外）§6 S3-2 的判据文字请按本节改写，保持判据与实现一致。
