# 轻量级编辑器：竞品定位与能力评估（2026-10-28）

> **用途**：回答「my-editor 在开源轻量编辑器谱系里到底站在哪一格、对谁有用、下一步该补什么」。
> **性质**：能力评估 + 改进方向（**不是**采购选型结论；不推荐任何人从 VS Code 迁移过来做主力 IDE）。
> **数据口径**：本项目数字全部为 `.doc/` 与设计文档中的**实测值**；竞品数字为**公开量级参考**（未在本机复测，误差可能 ±50%），仅用于排序不用于定论。评分是「对某类用户的适配度」，不是绝对优劣。

---

## 0 结论先行（五条）

1. **坐标**：my-editor 是「**Chromium 内核的 Notepad++ 现代重制版**」——包体打进 3 MB 档（Notepad++ 级），功能面却铺到了 VS Code 的周边广度（终端 / Git / 差异 / 工作区搜索 / 大文件虚拟视图），但**语言智能是空白**（无 LSP / 诊断 / 语义补全）。它既不是 VS Code 的替代品，也不是 lite-xl 那类「几百 KB 的记事本」。
2. **唯一硬伤是内存，且改不动**：整体私有内存 263–268 MB，是 Notepad++ 的 6–8 倍、Sublime 的 3–5 倍。这不是优化力度问题，是 WebView2 的固定成本（应用自身仅 5.8 MB 私有）。已有专文论证下限 160–200 MB（`.doc/内存占用可行性分析-Sublime对比.md`）。**所以「轻量」只能对外解释为「安装包小 + 启动快」，说成「省内存」就是误导。**
3. **真实优势是「零安装成本 + 中文 + 周边能力密度」**：3.10 MiB 安装包、48–53 ms 出窗口、118 条命令全部走同一张表（菜单/快捷键/命令面板同源）、全中文界面、开箱即用的格式化/编码/日志/JSON-YAML/Cron 工具集。这些恰好是 Notepad++ 用户最想要但 Notepad++ 给不了的组合。
4. **最大的两个失分维度是「插件生态」和「语言智能」，且都不应通过加重来解决**。可行的补法是**用已有依赖做近似能力**：① 复用 Rust 侧 `search.rs` 的 ignore+regex 引擎做「工作区符号跳转」；② 复用 `run.rs` 的进程执行做「用户自定义命令」。两项都不新增依赖。
5. **三个「低成本高回报」的缺口不在功能而在可信度**：单实例（防 `session.json` 并发覆盖）、TTI 埋点（现在只有窗口出现时间）、README 内存披露。见 §7 最小可行集。

## 2 目标用户画像

### P1 主画像：「单机运维 / 后端 / 数据侧开发者」（评分权重基准）

- Windows 为主，日常动作是：看 200 MB 日志 → 改服务器配置 / YAML / JSON → 写一段 Python/Node 脚本试跑 → 抓个接口返回 → 转个格式。
- 已有 IDE 但**不想为「看一眼文件」启动 3 秒**；或公司机器内存吃紧。
- 中文界面是硬需求（Notepad++ 的中文支持靠语言包，VS Code 中文要靠插件）。
- 不需要：调试器、断点、重构、远程开发、团队协作编辑。
- 痛点排序：**打开快 > 不丢内容 > 大文件不卡 > 少装东西**。

### P2 次画像：「前端 / 脚本侧轻量主力」

- 用 VS Code 做主力，my-editor 作为「第二编辑器」：专门开日志、Markdown 笔记、临时脚本、diff 对比。
- 需要良好的 Markdown 双栏 + 导出、格式化、Git 快速暂存提交。
- 对内存不敏感（反正 VS Code 吃掉 1 GB），但对**手感**敏感。

### P3 边缘画像：「教学 / 老旧机器 / 内网离线环境」

- 内网不能装 VS Code（体积/审计），但需要一个能看代码、能跑脚本、带终端的工具。
- 3 MB 安装包 + 无 Node 运行时依赖，是这类场景的真实优势。

### 明确非目标（写下来比不做更重要）

| 非目标用户 | 原因 |
| --- | --- |
| 中大型工程团队（Java/Go/C++ 多模块） | 无 LSP → 没有跳定义、没有类型检查、重命名靠字符串搜索 |
| 需要调试 / 断点 / 分析器的场景 | 明确不做（轻量红线） |
| Vim 模态键位用户 | 不做模态；键位一律不改（2026-10-27 决策） |
| 需要团队统一配置 / 插件分发 | 无插件体系、无 workspace settings 继承 |

## 3 评估维度与权重

### 3.1 维度定义（把「实用维度」翻译成可打分项）

| 你说的维度 | 落到评分项 | 衡量方式 |
| --- | --- | --- |
| 好用性 | 编辑内核质量 | 多光标 / 查找替换 / 大文件 / 撤销树 / 高亮准确度 |
| 开发者适用性 | 语言智能 | 补全 / 诊断 / 跳定义 / 重命名（LSP 能力面） |
| 极致轻量 | 内存占用 + 安装体积 + 启动速度 | 私有内存 / 安装包 / 冷启动到可交互 |
| 功能全面 | 周边能力 | 文件树 / 搜索 / Git / 终端 / diff / 格式化 / 编码 |
| 操作简单 | 学习成本 | 键位熟悉度 / 是否有命令面板 / 界面语言 |
| （补充） | 生态与可扩展 | 插件 / 脚本 API / 主题 / 配置深度 |

### 3.2 两套权重（权重不同，结论完全不同——这是重点）

**权重 A（P1 主画像：个人 / 运维 / 单机）**

| 维度 | 权重 | 依据 |
| --- | --- | --- |
| 编辑内核质量 | 20% | 每天真正用到的只有编辑、查找、大文件 |
| 周边能力密度 | 15% | 「能顺手干完杂活」是替代 Notepad++ 的核心理由 |
| 语言智能 | 15% | 需要「够用」而非「完整」 |
| 启动与响应速度 | 15% | 「不想等」是第一动机 |
| 内存占用 | 10% | 重要但不至于为此放弃功能（P1 机器普遍 16 GB） |
| 生态与可扩展 | 10% | 有则更好，没有可忍 |
| 学习成本 | 10% | 键位沿用 VS Code 即可拿满分 |
| 安装体积与分发 | 5% | 只在离线/审计场景成为硬指标 |

**权重 B（团队 / 中大型代码库）**

| 维度 | 权重 |
| --- | --- |
| 语言智能 | 30% |
| 生态与可扩展 | 20% |
| 编辑内核质量 | 15% |
| 周边能力密度 | 15% |
| 启动与响应速度 | 10% |
| 内存占用 | 5% |
| 安装体积 | 3% |
| 学习成本 | 2% |

> 两套权重不是「哪个对」。**A 是「这个项目该按什么做」，B 是「如果它想进团队该按什么做」**。用 B 衡量它，等于拿尺子量温度。

**补充说明（2026-10-28）**：§3.2 的 8 个维度衡量「能力」。另有三个维度不适合混进同一加权（否则会和能力分重复计算），单独组成**第二条轴「上手与持有成本」**：**使用成本**（§11）、**学习成本**（§12）、**人性化设计**（§13）。两轴合成见 §14.1。这样拆的好处是能看清一件关键的事——**能力分靠加功能，成本分靠改已有代码，两者的资源账完全不同**。

### 6.1 资源实测/量级

| lite-xl | ~5 MB | — | ~100–200 ms | ~30–60 MB | 公开量级 |
| VS Code | ~100 MB | — | 2–5 s（含扩展更久） | 400–800 MB | 公开量级 |
| Zed | ~60–100 MB | — | <500 ms（GPU 首帧） | ~200–500 MB | 公开量级 |
| Lapce | ~30–50 MB | — | ~500 ms | ~150–300 MB | 公开量级 |
| Helix（TUI） | ~30 MB | — | <50 ms | ~30–60 MB | 公开量级 |

**两条必须写进 README 的事实**：

1. **启动 48–53 ms 是「进程创建 → 主窗口句柄出现」**，口径已如实标注在 11.19.1，但对外容易被读成「53 ms 就能打字」。首屏可交互（TTI）**尚未埋点**（11.19.5 明确记录）。这是当前对外口径最大的薄弱点——它不比竞品差，但**不可证明**。
2. **263 MB 私有内存里 262 MB 属于 WebView2 进程组，应用自身仅 5.8 MB 私有**（`.doc/内存占用可行性分析-Sublime对比.md` §1）。这个拆解是本项目最有说服力的一段辩护，但目前只存在于 `.doc/` 里，README 只写「运行（F5）」「已知取舍」，没有任何内存数字。

打分依据（E1，其余同法）：

| 编辑内核 | 4 | CM6 全套（多光标/撤销树/查找/折叠）+ 自绘 Minimap（`src/editor/minimap.ts`）+ 大文件虚拟视图（`src-tauri/src/commands/large.rs:19-32`）；扣分在无诊断 |
| 周边能力 | 5 | 文件树/搜索/Git/终端/diff/格式化/编码/格式转换/Cron/正则，28 个面板（`src/panels/`） |
| 语言智能 | 2 | 仅 `completeAnyWord`（`src/editor/input.ts:31`），>2 MB 直接不挂（`:60-71`）；全仓无 LSP/诊断 |
| 启动 | 4 | 出窗口 48–53 ms，TTI 未测 |
| 内存 | 2 | 263–268 MB 私有，架构性下限 160–200 MB |
| 生态 | 1 | 零插件、零脚本 API |
| 学习成本 | 5 | 中文界面 + VS Code 键位 + 命令面板（`src/app/commandTable.ts:123-311`） |
| 安装体积 | 5 | 3.10 MiB，比 Sublime 小 6 倍 |

**关于评分的免责**：Zed 在 A 权重下第一，是因为 A 里内存只占 10%；但 Zed 的 Windows 版本成熟度、中文生态、离线可用性都不如 my-editor，**实际选择时应打折**。这类评分只适合看「结构性差距在哪一列」，不适合当排行榜。

**结构性结论（比总分重要）**：
- 与 **Notepad++** 比：my-editor 在周边能力 +3、生态 −1.5，总分只领先 0.03。**赢的是「现代工具链」，不是「轻」**。
- 与 **Sublime** 比：差 0.23，几乎全部来自生态（1 vs 3.5）和语言智能（2 vs 2，持平）。**Sublime 用 Python API + Package Control 换走了这 0.23**。
- 与 **VS Code** 比：差 0.25，但差距集中在「语言智能 + 生态」两列，而这两列恰好**是它不打算要的**。所以这不是「差一点就追上了」，而是「两条不同的路，恰好在总分上交叉」。

## 7 推荐场景（什么时候用、什么时候别用）

### 7.1 强烈推荐

| 场景 | 为什么是它 |
| --- | --- |
| 看 / 分析大日志（100 MB–5 GB） | 只读虚拟视图 + 稀疏索引，24 MB 日志打开不增加内存（11.19.2 实测）。VS Code 在这个体积会卡到无法操作 |
| 内网 / 离线 / 审计环境 | 3 MB 安装包，无 Node 运行时，无遥测，`capabilities/default.json:5-16` 只放 6 条窗口权限 |
| 改配置 / YAML / JSON / Properties 的日常 | 编码检测（GBK 乱码识别）+ 换行符切换 + JSON↔YAML 互转，一次装完不用再找工具 |
| 「不想为看一眼文件等 3 秒」 | 双击即开，无欢迎加载流程 |
| Markdown 笔记 + 导出 Word/PDF | 双栏 + 滚动联动 + 本地图片内联到导出文件，这条比 VS Code 的插件组合更省事 |
| 临时跑一段脚本 / 试一个接口 | F5 直接跑 Python/Node/Java/cURL，内置 PTY 终端 |

### 7.2 可以用但别当主力

| 场景 | 边界 |
| --- | --- |
| 单人维护的小项目（< 5 万行，单语言） | 有文件树 + 搜索 + Git 足够；但改函数名只能靠工作区替换 |
| Git 日常提交 | 行级暂存 + 提交 + 拉推都有，但**无凭据管理**（`src-tauri/src/commands/git.rs:62-69` 设 `GIT_TERMINAL_PROMPT=0`），私有仓库 push 失败时没有可行动的引导 |
| Hex 查看二进制 | 不支持（v1.1 移出范围） |

### 7.3 明确不推荐

| 场景 | 缺什么 |
| --- | --- |
| 中大型 Java/Go/C++/TS 工程 | 无 LSP：没有跳定义、没有类型错误、没有安全重命名。这会让开发效率倒退 5 年以上 |
| 需要调试 / 断点 / 性能剖析 | 无调试器，且不应加 |

### 11.3 逐项说明（只讲 my-editor 的得失）

**C1 = 3.5：唯一失分点是「根目录没有 LICENSE 文件」。**

`package.json:1-13` 只有 `"private": true`，无 `license` 字段；仓库根目录无 `LICENSE` / `COPYING`。按著作权默认规则，**无许可证 = 保留所有权利**，企业内网部署时法务会直接卡住——而这恰好是 P3 画像（内网/审计环境）的核心场景。这个成本和它是不是"免费"无关，是**合规不确定性**。

> 成本：选 MIT 或 Apache-2.0，加一个文件 + README 一行，**5 分钟**。这是全文档中投入产出比最高的一项。

**C2 = 5：装完即用，零插件。** 语言高亮内置 8 种同步 + 9 种懒加载（`src/editor/languages.ts:16-50`），格式化走 Prettier 内置（懒加载）+ 系统 CLI，无任何"先装扩展"步骤。VS Code 装完打个 `.go` 文件是纯文本，这个差距是真实的。

**C3 = 4.5：命令面板 + 快捷键 + 右键三级入口齐全，扣 0.5 在"部分动作只能走鼠标"。**

- 118 条命令一张表派生（`src/app/commandTable.ts:81`、`:123-311`），菜单/面板/键位/设置页同源（`src/core/commands.ts:79`）；
- 43 个默认键位（其中 15 个 `fixed` 不可重绑，`src/app/commandTable.ts:294-310`）→ 28 个可重绑；
- 编辑器右键菜单二级分组且按语言/只读态过滤（`src/app/menuContent.ts:71-266`）。

**C4 = 2.5：这是 my-editor 最弱的一项，弱于所有对标项目。**

| 缺失 | 证据 | 后果 |
| --- | --- | --- |
| 无自动更新 | `src-tauri/Cargo.toml:15-32` 无 `tauri-plugin-updater` | 用户装了 0.3.2 就永远是 0.3.2，除非自己想起来去下载 |

| 无单实例 | 无 `single-instance` 插件 | 见 §13 原则 2 的副作用：两实例并发写 `session.json` |

**C5 = 3.5：恢复能力"中间偏上"，靠草稿兜底，但没有回收站。**

- 加分：草稿防抖自动保存 + 启动统一勾选恢复（`src/app/sessionHost.ts`）、脏标签关闭三选（`src/ui/dialogs.ts:254-308`）、退出三选默认聚焦"保存"（`:314-379`，`:378`）、批量关闭前统一落草稿（`src/main.ts:455-458`）；

## 14 三维合成：定位图与「免费提分」清单

### 14.1 双轴定位（能力 vs 上手与持有成本）

横轴 = §6.2 权重 A 能力分；纵轴 = 使用成本 / 学习成本 / 人性化三项均分。

| Zed | 3.88 | 3.97 | 高能力 / 高体验 |
| VS Code | 3.75 | **4.37** | 高能力 / 最高体验 |
| Sublime Text | 3.73 | 3.93 | 高能力 / 高体验 |
| **my-editor** | **3.50** | **3.67** | **中能力 / 中体验** |
| Notepad++ | 3.53 | 3.63 | 中能力 / 中体验（与本项目几乎重合） |
| Lapce | 3.15 | 3.27 | 低能力 / 低体验 |
| lite-xl | 3.00 | 2.97 | 低能力 / 低体验 |

**核心判断（修正 §0 的第 3 条）**：

> my-editor 的真实卖点**不是「比 VS Code 轻」**（在成本体验轴上它 3.67 < VS Code 4.37，因为运维与人性化拖了后腿），
> 而是 **「以 Notepad++ 级别的上手成本，提供远超 Notepad++ 的能力密度」**——两者成本体验几乎相等（3.67 vs 3.63），能力却差 0.03 且结构完全不同（Npp 强在生态与概念少，本项目强在周边能力与中文）。
>
> 这个措辞比「轻量」准确得多，也天然规避了被拿去比内存和被拿去比 LSP。

### 14.2 「零运行时成本」的提分清单（唯一不吃内存/包体的投入）

> 建议把这一批放在「符号跳转」「自定义命令」之前——后两者各需 1.5 天且都改变能力面，而这一批只改「已有的东西是否可信」。

### 14.3 三维结论一句话

- **使用成本**：4/7 项满分或接近满分，真实拖累是「运维（无更新/无同步/无便携）」和「合规（无 LICENSE）」，**不是钱**。
- **学习成本**：中文 + 5 个概念 + VS Code 键位，已经接近这类工具的理论下限；唯一大洞是**没有任何面向用户的文档**（L5=2），而这恰好是最便宜补的。
- **人性化**：强项在「状态常驻可见」（4 分，超过 Sublime），弱项在「错过的提示可找回」（2.5 分，设计意图正确但只接了一半线）；最伤的是**一条说谎的文案 + 一个不存在的日志目录**，两者都会直接损伤信任，且修复成本都低于 1 小时。

`npm run tauri build -- --no-bundle` 构建耗时 **13m34s**（LTO + opt-level=s + codegen-units=1），产物 `target/release/my-editor.exe`。

### 18.1 数据

| 项 | 实测 | 与基线对比 |
| --- | --- | --- |
| 裸可执行文件 | **12.31 MB** | 8.99 MB（0.3.1）→ **+3.32 MB（+37%）** |

### 18.2 体积增长的归因与处置

`cargo tree -p trash --depth 1`：

```
trash v5.2.9
├── log v0.4.34
├── scopeguard v1.2.0
└── windows v0.62.2   ← 3.3 MB 的主要来源
```

`trash` 依赖微软官方 `windows` crate（全量类型绑定），是本次体积增长的主因；`tauri-plugin-single-instance` 走 `windows-sys`，增量可忽略。

**结论：接受现状，但记录备选方案。**

- 现状仍在「安装包 < 15 MB」目标内：**实测 NSIS 4.33 MiB / MSI 5.88 MiB**（0.3.2 完整打包，构建 5m52s）。对比 0.1.0 的 3.10 / 4.04，用户实际多下载 **1.23 MiB**——远小于裸 exe 的 +3.32 MB 增量（代码段压缩率高），安装包相对 15 MB 目标仍有 3 倍余量。
- 若体积成为硬约束，备选是**只对 Windows 用 `SHFileOperationW`（`windows-sys`，项目已间接依赖）替代 `trash`**，可省约 3 MB；代价是 macOS / Linux 要另写分支或放弃回收站能力（当前 CI 三平台构建，故先不做）。

### 18.3 TTI 口径说明

641 ms 与「出窗口 48–53 ms」不是矛盾，是两件事：

- 48–53 ms = 进程创建 → 主窗口句柄出现（`11.19.1` 口径）
- 641 ms = 进程创建 → 首帧绘制完成（含 WebView2 初始化 + 配置载入 + 会话恢复 + 首屏渲染）

对外描述启动速度时应**同时给出两个数**，否则容易在被实测时被认为夸大。README 已按此口径更新。

## 21 第六批：放弃更改前快照 + 人工冒烟清单（2026-10-28）

### 21.1 放弃 Git 更改前的快照

`discard` 的内部动作（`git restore --worktree` / `git clean -f`）保持不变，在其**之前**插入快照：

| 项 | 实现 |
| --- | --- |
| 落点 | `<配置目录>/discard-backup/<epoch-ms>/<原相对路径>`，附 `manifest.json`（仓库根 / 时间 / 文件清单 / 跳过数） |

| 用户可见 | 确认框写明「会先备份、但应用内不提供一键还原」；成功后状态栏提示备份位置；FAQ 第 18 条给手动还原步骤 |
