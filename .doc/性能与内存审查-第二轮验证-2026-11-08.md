# 性能与内存审查（第二轮）：验证与修复记录

- 验证对象：《my-editor 性能与内存占用 · 第二轮深度审查》（2026-11-08）
- 核对基线：本地工作区当前代码（即 `bc66d65` 之后的修复版本）。报告声明其未取得 `bc66d65` 文件内容，全部判断基于 v0.8.0 基线与提交标题，因此本文按**实际代码**逐条落定。
- 约束：不改变现有功能；只做确定性缺陷修复与语义等价优化。
- 结论：报告指出的 12 个耦合点中，**3 条与实现不符（已满足或前提不成立）**，**4 条不构成现实问题（已说明证据）**，**2 条是真实缺陷，本轮已修**（同路径重开旧线程不停、关闭会话不停过滤）；其余为架构取舍，维持现状。

## 1. 耦合点逐条核对

| # | 报告判断 | 核对结果 | 证据 |
|---|---|---|---|
| C1 | `flush()` 后 15s interval / `visibilitychange` / `beforeunload` 会再触发 2–3 次 saveSession | **不成立** | `flush()` 先把 `sessionDirty` 置 false 并清 `sessionTimer`；三个入口都以 `sessionDirty \|\| sessionTimer` 为条件，flush 后均为假，重载前无用户操作不会改回。另：`beforeunload` 由 `location.reload()` 触发时同样不写 |
| C2 | `close_large_file` 是 async + spawn_blocking，必须 await 且先置位再 remove | **已满足** | 释放函数逐个 `await`；`large.rs` 的实现是「置位 `entry.cancel` → `remove` → 置位并移除过滤标志」 |
| C3 | 全局单槽 cancel 会导致「只停索引不停过滤」或「多标签只能取消最后一个」 | **部分成立** | 过滤确实独立于会话标志（设计如此：取消过滤不能停索引）。但「关闭标签只停索引」不成立——`release()` 原先会先调 `cancel_large_task`。真正的缺陷是**全局槽**：关闭标签 A 会误取消标签 B 的过滤；且 `close_large_file` 自身不取消过滤（逃生门 / 退出路径漏掉）。**本轮已改为按 id** |
| C4 | 取消检查只在循环顶部，最坏读完一整块 + `collect` + 一次 emit | **已满足（无需再改）** | `collect()` 已去掉；`drain_index` 的检查在 `step()` 之前，取消后下一轮直接返回，不再 emit。最坏成本 = 当前 4MB 块读完（SSD 上 <10ms 量级） |
| C5 | 过滤块内逐行正则无检查点 | **成立** | 一个 4MB 块可含十万行。**本轮已加**：每 1024 行检查一次（`i & 1023 == 0`），取消即跳出并置 `cancelled` |
| C6 | refresh 不响应取消；`followTick` 错误会挤占 `MAX_NOTICES` | **不成立（两处）** | refresh 续扫循环已检查会话 `cancel`；`followTick` 的 catch 写的是 `statusEl.textContent`，不是 `noticeStore`，且 `this.info !== info` 时直接返回 |
| C7 | Watch / TreeWatch 旧注册会占满槽位，新前端注册静默失效 | **不成立** | `watch_files` / `watch_dirs` 都是**全量替换**语义：每次都重建 `known` 与 `dirs`，目录集合变化才重建 watcher，旧 watcher 被 drop 即注销。`MAX_WATCH_DIRS=200` 是单次集合上限，不是累计配额 |
| C8 | `PathGuard` 无 `remove_path`，每次重载只增不减 | **事实成立，影响可忽略** | 只影响写入类作用域，且只随「打开过的不同路径」增长（HashSet 去重），重启清空；重载后会话会恢复这些文件，保留授权符合用户意图。加 `remove_path` 需前端维护生命周期，收益不匹配 |
| C9 | `terminal_close` drain 后输出线程不 join，仍会 emit | **不成立（无泄漏）** | `Session` drop 时 master/writer/child 释放、子进程被 `taskkill` 结束；读线程在 `read()` 返回 0/错误时退出，flush 线程在 `rx` Disconnected 时退出。未保存 JoinHandle 只是无法同步等待，不是线程泄漏 |
| C10 | 统一释放可能漏掉 `stop_run` | **不成立（已覆盖）** | `releaseBackendResources()` 第一项就是 `invoke("stop_run")` |
| C11 | `dispose()` 若只 unlisten 不清空数组，`ensureListeners` 会拒绝重注册 | **不成立（已满足）** | `LargeView.dispose()` 里 `this.unlisteners.length = 0`，且只由退出 / 重载调用；`close()` 保持不解除订阅 |
| C12 | `TerminalHost.dispose()` 不重置 `listenersReady` | **不成立（新实例）** | 重载后 `main.ts` 重新执行、`TerminalHost` 重建；同一实例在 dispose 后复用不属于现有路径 |

## 2. 报告 §4 的三条二阶风险

| 项 | 结论 | 说明 |
|---|---|---|
| §4-1 同路径「开→关→开」取消竞态 | **部分成立，已修旧线程残留** | 实现每次 `open_large_file` 新建 `Arc<AtomicBool>`，不会复用旧标志（不存在「新会话误用旧标志」）。但旧 entry 被 `map.insert` 覆盖时，**旧索引线程没有被取消**，会读完整文件才在末尾发现 session 过期。本轮在 insert 前置位旧 entry 的 `cancel` |
| §4-2 重载触发大文件重新索引 | **属实，属取舍** | 首扫 8MB（`FIRST_SCAN_BYTES`）+ 后台补齐剩余；重载语义就是「干净重放会话」，复用旧索引需要后端按 path 复用 entry，会与「释放资源」的 P0 目标冲突。重载是低频手动操作，维持现状 |
| §4-3 取消后仍 emit 一批事件 | **不成立** | 取消检查在 `step()` 之前，`on_step`（进度 emit）只在成功读块后调用；取消后不会再有进度事件 |

## 3. 本轮改动

### 3.1 过滤取消按会话 id（C3 / C5）

`src-tauri/src/commands/large.rs`：

- `LargeState.cancel: Mutex<Option<…>>` → `filter_cancel: Mutex<HashMap<String, Arc<AtomicBool>>>`。
- `filter_large_blocking` 开始登记 `map[id]`，并取消该 id 上一次仍在跑的任务；结束时只清理自己登记的项。
- `cancel_large_task(state, id: Option<String>)`：带 id 精确取消，不带 id 全量取消（退出 / 重载兜底）。
- `close_large_file` 在移除会话后同时置位并移除该 id 的过滤标志：逃生门 / 退出流程即使没先调 `cancel_large_task`，过滤也会停。
- 过滤行循环每 1024 行检查一次取消；取消时不再累加 `line_no`（结果本身丢弃）。

### 3.2 同路径重开取消旧索引线程（§4-1）

`open_large_file_blocking` 在 `map.insert` 前，若同 path 已有 entry，先置位其 `cancel`。

### 3.3 前端配套

- `LargeView.cancel()`：有当前会话时传 `{ id }`，未绑定会话时退回全量（空操作）。
- `LargeFileHost.release(tab)`：改为 `invoke("cancel_large_task", { id: tab.largeId })`，不再调用视图的全局取消——关闭标签 A 不会中断标签 B 的过滤。

### 3.4 不改的项

C1（不会重复 IPC）、C4（4MB 粒度已足够）、C6（写状态行不是通知中心）、C7 / C9 / C11 / C12（与实现不符或无可观察影响）、C8（PathGuard 增长受打开过的路径数限制）、§4-2（重载语义取舍）。

## 5. 复测建议（对应报告 R 系列）

| 场景 | 判据 | 本轮对应改动 |
|---|---|---|
| R2 / R6：200MB 索引中关闭 → 同路径重开 20 次 | `totalLines` 不回退；CPU 5s 内回落 | 3.2 |
| R3：两个大文件并行索引，只关其中一个 | 另一个继续、被关的立即停 | 会话级 `cancel`（上轮）+ 3.2 |
| R4：过滤中关闭标签 / 走「以编辑器打开」 | 无「会话已关闭」错误；CPU 不再上升 | 3.1 |
| R7：大文件视图关闭再打开 | 索引进度事件仍到达 | 上轮 `dispose()` 与 `close()` 分离 |
| R1 / R5 / R8 | 见上轮记录；R8 的 <4MB 判据需按「首扫 8MB」修正 | 未改 |

注：报告 R8 的判据「重载后磁盘读 < 4MB」与实现的首扫阈值 `FIRST_SCAN_BYTES = 8MB` 不一致，实际应设为「≈8MB + 首窗读取」，且重载语义本就要重建索引。
