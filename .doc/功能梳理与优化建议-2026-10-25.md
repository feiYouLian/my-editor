# 功能梳理与优化建议（2026-10-25）

> 范围：仓库当前 HEAD 的全部前端模块（`src/**`）、Rust 侧 IPC 命令清单（`src-tauri/src/lib.rs`）、
> 配置体系（`src/config/settings.ts`）与既有设计文档（`轻量级编辑器_易实现功能清单.md`、`重构计划.md`）。
> 方法：逐模块读代码确认能力与入口，配置项逐个追消费点，历史设计文档与现状对账。
> 结论只写"有代码依据"的项；行号为当前快照，动手时以符号名定位。

## 一、结论摘要

能力密度已经很高（约 60 项可用能力，覆盖打开/保存/编码/格式化/运行/终端/比较/转换/工具），
主要问题不在"缺功能"，而在四处：

1. **一个可见缺陷**：文件树的目录加载令牌是实例级单一计数，多目录并发加载互相作废——
   恢复多个展开目录、或任何一次刷新后，**只有一个目录能显示子项**（详见 §四 P0-1）。
2. **高频操作缺位**：无跨文件搜索、无文件快速打开（Ctrl+P）、无代码折叠、无全部保存、
   无拖放打开。前两项是"文本编辑器"与"项目编辑器"的分水岭。
3. **已有能力的出口不足**：工具类命令没有一级菜单、命令面板不显示快捷键、状态栏编码菜单
   只有"重新解释"没有"另存为编码"、标签栏无 "+" 按钮、首屏空态无引导。
4. **配置承诺与实际不一致**：`formatOnSave` / `search` / `ignoreDirs` / `globalReplace` /
   `fileEncodingMemory` / `ai` / `log` 无消费点；反向地，`settingsHelp` 把已实现的
   `session` / `workspace` / `largeFile` 两项标成了"预留"。

## 四、功能缺陷（建议先修）

### P0-1 文件树多目录并发加载互相作废（可见 bug）

- 位置：`src/panels/fileTree.ts` 的 `loadChildren` / `createNode` / `loadToken`。
- 机制：`loadToken` 是**实例级单一计数器**，每次 `loadChildren` 先 `++loadToken`，`await` 后
  用 `token !== this.loadToken` 丢弃过期结果。而 `render()` 会对**每个已展开目录**调用
  `loadChildren`，这几次调用同步自增令牌，因此**只有最后一次调用的结果能落地**。
- 触发场景（都很常见）：
  1. 启动恢复工作区时展开 2 个以上目录 → 只有最后一个目录有子项，其余展开但空白且不重试；
  2. 新建文件 / 重命名 / 删除 / 点"刷新"后 `render()` → 同样只保留一个目录的内容；
  3. 快速连续展开 A、B 两个目录 → 先点的 A 空白。
- 修复：令牌改为按目录维度（`Map<string, number>` 或写入 `container.dataset.token`），
  或每个容器一个 `AbortController`；保留 `container.isConnected` 的失效判断。
- 验收：展开 A/B/C 三个目录 → 点刷新 → 三者都有内容；快速连点 3 个目录 → 全部加载成功。

### P0-2 配置说明与实现相反（误导）

- `src/ui/settingsHelp.ts` 把以下**已实现**项标为"预留（未接入）"：
  - `session`：`main.ts bootstrap` 已用于恢复会话，`app/sessionHost.ts` 负责草稿；
  - `workspace`：`services/workspace.ts` + `fileTree` 持久化在用；
  - `largeFile.sparseIndexAnchorBytes`：`app/largeFileHost.ts` 使用；
  - `largeFile.viewportPaddingLines`：`app/tabSwitcher.ts` 使用。
- 反向问题：`formatOnSave` 确实是"预留"（无任何消费点），但 `config.json` 与
  `EditorSettings` 都暴露它，用户改了没效果。
- 建议：以"是否存在消费点"重排 effect 列；真预留项收敛到单独分组，并在设置面板隐藏；
  `formatOnSave` 二选一——接入（见 §五 B-19）或从配置与说明中移除。

### P0-3 formatters 前后端白名单不一致

- 前端 `src/config/formatters.ts` 的 `cliFormatters` 决定 `supportsFormatting()`；
  后端 `run_cli_formatter` 按 `config.json.formatters` 解析工具与参数（防 RCE）。
- 影响：用户在 config.json 里新增一门语言的 CLI 格式化器（如 `kotlin`），前端仍判"不支持"，
  请求根本不会发到后端。内置表只应承担"安装指引 + 默认值"。
- 建议：`supportsFormatting` 改为 `key in jsFormatters || key in getConfig().formatters`；
  安装指引对未知工具给通用文案。

### P0-4 外部修改只有一个出口

- 现状：状态栏"外部修改"点击直接 `reloadFromDisk`（脏则确认丢弃），没有"对比"入口。
- 建议：点击弹三选——重新载入 / 与磁盘比较 / 忽略。`diff_files` 与 `diffService` 已具备能力。

## 七、信息架构建议（页面级）

1. **首屏有内容**：欢迎页（打开文件 / 打开目录 / 最近打开 / 4 条常用快捷键），替代空白编辑区。
2. **侧栏 tab 化**：文件树 / 搜索 / 大纲，三个高频视图固定位置，避免"功能藏在命令面板"。
3. **菜单栏补齐**：文件、编辑、选择、转到、**视图**、**工具**、比较、设置、帮助（关于）。
   视图：侧栏/终端/输出/命令面板/主题；工具：Cron/正则/批量编码/格式转换/最近打开。
4. **命令面板承担"发现层"**：所有命令 + 快捷键 + 最近使用；文件快速打开作为第二种 Provider。
5. **状态栏分层**：左侧文件属性（可点）+ 右侧计数与状态；消息区升级为通知中心（可回看）。

| 不做 | 理由 |

| 插件系统 / 宏录制 | 与"轻量"定位冲突，安全边界（RCE）成本极高 |
| 完整 LSP / 智能补全 | 依赖重、启动慢；当前定位是文本/脚本工具而非 IDE |
| 多窗口 / 分屏编辑器 | 状态机与布局复杂度翻倍，收益集中在小众场景 |
| 主题市场 / CSS 注入 | 维护成本高；先把"跟随系统"做对 |
| TODO 独立面板 | 并入全局搜索的预设查询更划算（C-24） |
